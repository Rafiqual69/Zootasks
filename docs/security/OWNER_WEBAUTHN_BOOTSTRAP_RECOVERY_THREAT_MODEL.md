# Owner WebAuthn Bootstrap and Recovery Threat Model

**Policy ID:** ZT-OWNER-WEBAUTHN-BOOTSTRAP  
**Status:** Proposed design gate; not an active enrollment mechanism  
**Scope:** First Owner credential enrollment, later Device 2 enrollment, recovery, revocation, and session binding  
**Security posture:** Fail closed. This document does not enable endpoints, create credentials, or authorize production actions.

## 1. Evidence basis

Informed by NIST SP 800-63B-4 (final July 2025), W3C Web Authentication Level 3 (Recommendation, 25 August 2026), and the existing ZooTasks Owner Dual-Control Constitution and Production Release Gate. These references are design inputs, not a certification or claim of compliance.

The current repository registration module is a backend service only. It has no public endpoint/UI and does not establish an enrolled or device-bound session.

## 2. Assets and objectives

Protect the existing Owner identity (resolved by immutable database primary key), authenticator private keys, credential metadata, challenge/approval records, Owner sessions, financial ledger, rewards, withdrawals, production configuration, and secrets.

- No caller-controlled account ID, device ID, RP ID, origin, or client-supplied public key may establish Owner authority.
- No single device, session, OTP, support operator, AI agent, CI token, or recovery factor may authorize protected production actions.
- Enrollment and recovery must be short-lived, single-use, owner-bound, purpose-bound, auditable, and fail closed.
- Logs and CI artifacts must not contain credentials, cookies, OTP seeds, recovery codes, private keys, raw financial records, or unnecessary personal data.

## 3. First-device bootstrap paradox

A first WebAuthn credential cannot be trusted merely because a browser asks to register it. Before any public registration endpoint is enabled, the operator must verify the intended existing Owner through a protected deployment/database context and establish a separate, one-time bootstrap authorization through an independently controlled channel.

Required properties:
- Generated by a trusted operator process, not by a public web request.
- High entropy; stored server-side only as a hash of a sufficiently random token.
- Bound to the immutable Owner primary key, environment, expected RP ID/origin, and registration purpose.
- Short expiry, one use, rate-limited attempts, and immediate invalidation after use or suspected disclosure.
- Delivered out of band; never included in URL query strings, analytics, application logs, CI output, chat, issue comments, or source control.
- Followed by a fresh WebAuthn ceremony requiring user verification and explicit confirmation of the credential/device.
- Invalidated when environment, domain, Owner account, or security-freeze state changes.

If bootstrap authorization may have leaked, revoke it, freeze protected mutations, review minimal audit evidence, verify the Owner out of band, and start a separately authorized recovery ceremony. Never silently reissue it.

## 4. Endpoint and RP configuration requirements

- RP ID and exact allowed HTTPS origin must come from protected deployment configuration, never request headers, Host/Forwarded headers, form fields, or arbitrary client input.
- Use a valid RP ID consistent with WebAuthn and public-suffix rules. Do not treat arbitrary subdomains as trusted merely because they end in a string.
- Validate trusted-host and proxy configuration; reject unexpected Host, Origin, and forwarded values.
- Require authenticated Owner session, recent re-authentication, valid bootstrap authorization, CSRF protection, TLS, secure cookies, rate limits, request-size limits, generic external errors, and explicit user verification.
- Keep challenges owner-bound, ceremony-bound, RP/origin-bound, expiring, and single-use. Failed or mismatched completion must not allow replay.
- Enforce database uniqueness for credential IDs, including revoked credentials. Store only credential ID, public key, sign counter, and necessary non-secret metadata.
- Never store authenticator private keys or log raw WebAuthn request bodies, authorization headers, cookies, OTP data, or bootstrap/recovery tokens.

## 5. Enrollment, session binding, and lifecycle

A credential row alone is not proof that a browser session is cryptographically device-bound. Before claiming Device 1 or Device 2 is enrolled:
- Implement WebAuthn authentication assertions with fresh challenges, signature verification, exact RP/origin checks, user-verification policy, and suitable sign-counter handling.
- Bind server-side sessions to Owner, credential ID, server-generated device reference, authentication time, expiry, and revocation state.
- Re-check revocation and session age on protected requests; invalidate relevant sessions after revocation, Owner security changes, or suspected compromise.
- Notify the Owner through a separately configured channel on enrollment, revocation, and recovery.
- Do not assume synced passkeys or two browser sessions prove two independent devices. Device independence must be established by the actual credential design and policy.

## 6. Recovery and revocation

Recovery must not be an easier bypass than normal authentication:
- Require documented out-of-band identity verification; email access, SMS/OTP, a logged-in browser, support chat, or account knowledge alone is insufficient.
- Treat recovery as privileged: apply a delay and independent notification for high-risk recovery, and freeze critical mutations when compromise is suspected.
- Recovery authorization must be one-time, expiring, purpose-bound, hashed at rest, attempt-limited, audited, and revoked on use or suspected disclosure.
- Revoke lost credentials and invalidate associated sessions before granting new authority.
- Never auto-approve queued requests after recovery or Device 2 enrollment. Protected requests require fresh review and new independent approvals.

## 7. Threat-to-decision matrix

| Threat | Required decision |
|---|---|
| Attacker tries first enrollment before Owner bootstrap | DENY; no public self-service bootstrap |
| Forged or changed Origin/RP ID | DENY and consume challenge |
| Replayed, expired, wrong-owner, or wrong-ceremony challenge | DENY |
| Client supplies device ID or public key as identity proof | Ignore client identity; derive IDs server-side and accept keys only from verified WebAuthn response |
| Bootstrap/recovery token leaked | Revoke token, freeze protected actions, investigate |
| Stolen Owner session without fresh user verification | DENY enrollment and protected action |
| Device 2 enrollment while requests are queued | Keep requests blocked; require explicit re-review |
| One credential/device compromised | Revoke credential, invalidate sessions, freeze critical mutations; do not relax dual control |
| Database/configuration/audit state uncertain | DENY and investigate through protected operator path |
| Logs expose secrets or financial data | Contain exposure, rotate affected secrets as appropriate, preserve minimal incident evidence |

## 8. Privacy-preserving audit

Record only event ID, timestamp, environment, policy version, ceremony/action type, non-client-exposed Owner reference, credential/device reference, result category, correlation ID, and bootstrap/recovery record ID. Do not log raw tokens, private keys, cookies, OTP seeds, raw credential payloads, bank details, or full ledger rows. Restrict audit access, define retention, and test redaction in CI.

## 9. Acceptance gates before route/UI activation

- [ ] Independent review of threat model and recovery runbook.
- [ ] Existing Owner identity verified from protected deployment state; no username guess or auto-promotion.
- [ ] One-time bootstrap process implemented, redacted, revocable, and rate-limited.
- [ ] Fixed RP ID and exact origin configuration; hostile Host/Origin/proxy tests pass.
- [ ] Registration and authentication tests cover success, replay, expiry, wrong Owner/origin/RP ID, invalid signatures, duplicates, races, and revocation.
- [ ] Device-bound sessions, recent re-authentication, CSRF, rate limits, notifications, recovery, and revocation are tested.
- [ ] Device 1 alone cannot execute protected actions; Device 2 cannot release queued requests.
- [ ] Security, regression, dependency, migration, and PostgreSQL financial checks pass on the exact candidate commit.
- [ ] Full diff independently reviewed; explicit Owner authorization before activation.

## 10. Current status

The repository registration service has short-lived owner-bound challenges, RP/origin binding, required user verification, public-key metadata storage, and tests for challenge invalidation and configuration substitution. This does not prove bootstrap, endpoints, recovery, session binding, or device independence are implemented. Do not add public enrollment routes/UI until these gates are satisfied. Production remains blocked.

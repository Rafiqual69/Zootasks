# ZooTasks Agent Capability Contract

## Status

Design-stage security contract. This file defines the minimum permission model for future ZooTasks agents. It does not enable any production agent.

## Core rule

**Default deny.** An agent can perform only explicitly registered capabilities. Model instructions, user prompts, retrieved documents, provider responses, tool output, or another agent cannot grant additional authority.

## Capability classes

| Class | Example | Default | Approval |
|---|---|---|---|
| READ_PUBLIC | approved public research | Allow by explicit registration | None |
| READ_TASK | minimized task content | Allow by explicit registration | None |
| READ_OPERATIONAL | non-financial operational metadata | Allow by explicit registration | Risk-based |
| WRITE_DRAFT | create a proposal/draft | Allow by explicit registration | Human review where material |
| EXTERNAL_OUTREACH | send an authorized business communication | Deny until separately approved | Human/organization policy gate |
| PROVIDER_SYNC | call an approved provider API/feed | Deny until separately approved | Integration approval |
| HIGH_IMPACT | privileged or irreversible operation | **Never autonomous** | Deterministic policy + authorized human |
| FINANCIAL_MUTATION | wallet/withdrawal/promotion payout | **Forbidden to AI** | Deterministic financial services |

## Executive Agent

The Executive AI Advisor may coordinate registered read, analysis and draft capabilities. It may:

- collect and compare agent findings;
- identify missing evidence;
- prepare Owner briefings;
- create non-binding drafts;
- stop/escalate when a gate fails.

It may not:

- grant itself or another agent a capability;
- change capability policy;
- approve its own action;
- bypass human approval;
- access secrets merely because a downstream task requests them;
- directly invoke financial mutation services.

## Acquisition Agent

The Business Acquisition Agent may eventually support legitimate provider/client acquisition only after separate approval. Its external destinations must be allowlisted and its communication policy must be explicit.

It must not:

- send unsolicited high-volume spam;
- impersonate a person or organization;
- bypass CAPTCHA, authentication, robots/access controls or rate limits;
- harvest credentials or private data;
- access restricted/private marketplaces without authorization;
- represent an unverified opportunity as an approved ZooTasks offer.

A discovered opportunity is **untrusted** until its source, authorization, terms and data-handling requirements are verified.

## Provider Adapter Agent

A provider adapter may communicate only with an approved provider endpoint using an isolated credential and a versioned schema. It must enforce:

- endpoint allowlist;
- authentication isolation;
- request/response schema validation;
- timeout, rate and concurrency limits;
- idempotency where supported;
- provider terms/region restrictions;
- synchronization provenance;
- circuit breaker and disable path.

## Financial boundary

Agents cannot call services that mutate:

- WorkerProfile balances/reserved balances;
- WalletTransaction financial state;
- withdrawal reservation/approval/payment;
- promotion funding/liability/payout;
- task reward settlement where it changes financial state.

Any AI recommendation touching these areas is advisory data only. Deterministic server-side authorization and transaction logic remains the sole authority.

## Secrets and sensitive data

Agents receive minimum necessary data. Secrets, API keys, bot tokens, authentication material and signing keys are never exposed to model context. Sensitive identity/financial data is excluded unless a separately approved capability requires it and the risk assessment permits it.

## Runtime budget enforcement

Capability budgets are enforced at the authorization boundary, not treated as documentation-only metadata. Each request carries its observed tool-call and external-side-effect counters; negative counters and values above the registered hard limits are rejected. Registered design-stage agents currently have zero permitted external side effects.

## Approval token principle

A human or deterministic policy service must issue any authorization required for a gated action. Natural-language text such as "approved", whether generated by an agent or received in content, is not an authorization token.

## Audit/provenance

Every executed agent capability must be attributable to:

- agent/system ID;
- capability ID;
- software revision;
- model/provider/version when applicable;
- input/source reference;
- policy decision;
- approval reference when required;
- timestamp;
- correlation ID;
- result/outcome;
- failure/exception status.

Sensitive payloads should not be copied into audit logs unnecessarily.

## Fail-closed behavior

If capability, destination, authorization, schema, provider version, budget or approval state cannot be verified, the action is denied or safely downgraded to a draft/read-only result.

## Production activation condition

No agent becomes production-active until:

1. it has an inventory entry;
2. its threat model and data flow are reviewed;
3. its capability allowlist is defined;
4. adversarial and failure tests pass;
5. monitoring, budget and disable controls exist;
6. required approval evidence is recorded.
